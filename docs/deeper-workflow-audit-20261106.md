# Deeper employee and buying-to-selling scan — 6 November 2026

## Result

This pass confirmed **14 additional gaps**: ten live database boundary failures, three application recovery/privacy failures and one recruitment compatibility regression. This report preserves the original audit state. The subsequent [repair and staging verification record](deeper-workflow-fixes-20261106.md) documents the fixes.

The most urgent findings are simulated mobile-payment success, direct manager stock writes, an alternate delivery-status write path and unreviewed catalog creation. The reviewed workflow commands can enforce their own checks while older table policies still permit an alternate path.

## Confirmed findings

### 1. Critical — STK payment success is generated by a timer

`usePOSMobilePayment.triggerStkPush` moves from sending to pending, then success after 700 ms plus six seconds. It creates a plausible random M-Pesa reference without making a provider request. `isMobilePaymentReady()` then returns true, enabling checkout. The UI says the PIN was confirmed and the amount received.

**Reproduction:** the hook test advanced timers by 6,700 ms; success, a generated reference and checkout readiness appeared with no fetch call. The hook imports no payment transport. This behavior is in the normal hook, without an environment-only simulation gate.

**Repair:** remove simulated success from the operational path. Use a trusted provider-confirmed transaction bound to country, merchant, amount, currency and sale, or an explicitly recorded manual verification workflow. Missing integration must remain unavailable/pending. Do not claim PIN confirmation from a timer.

Evidence: `tests/audits/deeperMobilePaymentGap.test.tsx`; `components/pos/hooks/usePOSMobilePayment.ts`; `components/pos/modals/MobilePaymentSection.tsx`; `components/pos/modals/PaymentModal.tsx`.

### 2. High — warehouse managers can change stock without an adjustment request

An authenticated Adama warehouse manager directly increased a synthetic product's stock by **999 units**. No inventory request or active job was supplied. `enforce_product_update_restrictions` expressly allows manager stock changes after the table policy admits the row.

**Impact:** the reviewed stock-adjustment process is bypassable through direct API writes, undermining inventory accountability.

**Repair:** require a transaction-bound approved adjustment or verified physical-operation posting for every stock mutation. Site authority alone must not grant stock authority.

Evidence: `tests/sql/deeper_workflow_boundary_scan.sql`, observation `manager_changes_stock_without_request`; live `products_update` policy and `public.enforce_product_update_restrictions`.

### 3. High — direct sale updates can claim delivery without warehouse work

The same warehouse manager changed a synthetic sale from Picking to **Delivered**, and set its release status to RELEASED, without a pick, pack or shipment. The financial-field guard leaves these fields writable; `salesService.update` also forwards supplied fields through a broad spread.

**Impact:** delivery reporting can diverge from physical movement and stock posting. The repaired order-release command passes its own regression, but this alternate write path remains open.

**Repair:** bind fulfillment transitions to saved pick/pack/shipment evidence and restrict direct sale updates to a narrow allowlist.

Evidence: workflow scan observation `manager_marks_delivery_without_warehouse_work`; `services/sales.service.ts` update method; live `sales_update`, `guard_sale_financial_mutation` and `stamp_counter_sale`.

### 4. High — receiving placeholders can contain unreviewed approved prices

An authenticated receiver inserted a zero-stock On Order product with **price 1** and **approval_status approved**. No merchandising decision was required. The placeholder INSERT policy validates stock/location and staff scope, but does not force pending approval or protect commercial fields. The unpriced-product trigger only forces pending when price is zero or negative.

**Impact:** a receipt-side catalog creation can bypass commercial review. This reproduction did not change an existing stocked lot's price or complete a receipt into the new record.

**Repair:** derive placeholder identity from approved procurement/catalog evidence and force unreviewed commercial values into a held state. Require a reviewed commercial command before sale eligibility.

Evidence: workflow scan observation `receiver_publishes_unreviewed_price`; live `products_insert_receiving_placeholder` and `private.hold_unpriced_product_for_approval`.

### 5. High — floor staff can create completed financial sales without a counter

An authenticated receiver created a Card sale at the warehouse by setting type to Delivery. The result was **Completed** with no shift. The sale RPC checks active employment and site scope, but does not restrict the actor to a sales role. The counter trigger allows any non-Delivered sale to omit a counter.

**Impact:** operational staff can originate completed financial transactions through an alternate sale type. This is not evidence that a card charge occurred.

**Repair:** separate counter checkout from authorized delivery-order creation. Enforce sales authority and payment lifecycle on the server for each path; a client type value must not select a less restrictive financial boundary.

Evidence: workflow scan observation `receiver_creates_completed_card_sale_without_counter`; live `create_pos_sale_atomic` and `stamp_counter_sale`.

### 6. High — Mobile Money sales do not require transaction evidence on the server

The sale RPC accepted a Mobile Money sale as Completed with no transaction reference or channel. The database constraint only validates reference shape **when a reference is supplied**. The POS form's reference requirements therefore do not protect direct requests.

**Repair:** require trusted payment evidence or a clearly identified manual verification decision, and prevent reuse against another sale. Merely requiring a typed string would not resolve simulated/provider-unverified success in finding 1.

Evidence: workflow scan observation `mobile_sale_without_transaction_reference`; live `pos_mobile_reference_shape` and `create_pos_sale_atomic`; UI readiness checks in `usePOSMobilePayment.ts`.

### 7. High — a receiver can read another site's sales

The Adama warehouse receiver selected a synthetic sale belonging to another Ethiopian store. `sales_isolation_select` grants employees access to sales throughout their home country, rather than limiting floor roles to their active site. Client filters cannot close this API path.

**Repair:** enforce site reads for branch workers and explicit oversight scope for managers. Preserve country isolation separately.

Evidence: workflow scan observation `receiver_reads_other_site_sale`; live `sales_isolation_select` policy.

### 8. High — blind receiving quantities remain readable through PO items

The receiver selected the exact expected PO line quantity, **37**, directly from `po_items`. Its SELECT policy admits every line whose parent PO is visible. Hiding the count in the receiving modal does not protect this separate API projection.

**Repair:** provide a count-safe receiver projection/command and restrict underlying expected quantities until the appropriate stage. Manager exception evidence can remain available through authorized review.

Evidence: workflow scan observation `receiver_reads_expected_po_quantity`; live `po_items_zero_trust_select` policy.

### 9. High — independent HR activation bypasses hiring quota and salary limits

With a fixture quota of **zero** and salary ceiling of **1**, a warehouse manager created a pending picker with salary **1,000,000**. A different regional HR actor activated that employee without Finance clearance, an executive exception or a reviewed candidate. Independent HR identity is enforced, but budget/quota evidence is not.

**Repair:** bind activation to server-evaluated quota, current headcount and compensation policy. Require the applicable Finance/executive exception signatures and recheck the limits in the same locked transaction.

Evidence: `tests/sql/deeper_employee_boundary_scan.sql`, observation `hr_activates_over_quota_and_salary_band_without_finance`; `private.guard_employee_authority`; `services/recruitment-delegation.ts`.

### 10. High — the approved recruitment path conflicts with the onboarding guard

`provisionActivatedEmployee` still inserts status Active. The current database rejects that insert for every non-CEO actor, including HR. A candidate with HR and hiring-manager approval reaches this incompatible write through Finalize activation.

This is a compatibility regression from the prior onboarding hardening. The correct response is to connect recruitment to the independent trusted activation workflow, not to remove the pending-hire protection.

Evidence: application reproduction in `deeperEmployeeRecoveryGaps.test.ts`; live observation `non_ceo_active_insert` returned “New employees require independent onboarding approval”; `services/recruitment-delegation.ts:176` and `recruitment.service.ts`.

### 11. High — disciplinary notices can target an employee in another country

An ET regional HR actor inserted a notice labeled ET/Adama for a synthetic employee assigned to a KE site. The policy checks the notice's supplied site/country but does not bind them to the employee's actual workplace.

**Repair:** derive employee identity, workplace and country from the trusted target, and authorize that target before insertion. Preserve historical identity on later updates.

Evidence: employee scan observation `et_hr_issues_notice_for_ke_employee`; live `disciplinary_insert_scoped` policy. No real employee received a notice.

### 12. High — notice issuers can adjudicate their own appeals through the API

The same HR actor inserted a pending-appeal notice and directly changed it to Upheld. There is no disciplinary decision trigger enforcing an independent reviewer. The service's maker/checker check depends on a local cached record and can be bypassed by direct requests.

**Repair:** use an atomic appeal decision command with authenticated issuer/reviewer IDs, distinct actors, immutable evidence, pending-state locking and a required decision reason.

Evidence: employee scan observation `notice_issuer_adjudicates_own_appeal`; live `disciplinary_update_scoped`; `disciplinaryService.resolveAppeal`.

### 13. High — disciplinary persistence failures are acknowledged as completed actions

Denied notice insertion still returned a generated notice and logged an issued event. Denied appeal filing and denied adjudication both returned true. The screens then show successful submission/resolution. Local backup changes are presented as server completion.

**Repair:** propagate save failures; verify the persisted result before success/audit claims. Any supported offline proposal needs explicit queued state and a trusted retry contract, not a completed disciplinary outcome.

Evidence: three failure reproductions in `deeperEmployeeRecoveryGaps.test.ts`; `services/disciplinary.service.ts`; `AppealModal.tsx` and `DisciplinaryRegisterTab.tsx` success paths.

### 14. High — denied personnel reads can reveal a previous user's disciplinary cache

After seeding the shared disciplinary backup as a previous user, a denied read returned its confidential notes to the current session. The storage key is not tied to user/session. The register asks for the country without a site filter, increasing the data retained on shared devices.

**Repair:** remove sensitive cross-session fallback, fail closed on denied reads, scope bounded queries to authorized targets, and clear any legacy personnel backup. Do not let cached data override a current authorization denial.

Evidence: denied-read reproduction in `deeperEmployeeRecoveryGaps.test.ts`; `getLocalBackup`, `saveLocalBackup`, `fetchDisciplinaryRecords`; the register's `loadRecords`.

## Controls rechecked and retained

All six scripts below passed on staging and rolled back:

- `employee_audit_controls_that_hold.sql`: direct offboarding, cross-country sale creation and terminated-worker sale creation denied.
- `employee_fixed_authority_privacy.sql`: executive appointment, confidential base-column reads, self metrics and cross-country schedule writes denied.
- `employee_fixed_payroll.sql`: roster snapshot, independent signatures, regional attestation, atomic unpaid expense and independent settlement retry preserved.
- `deep_integrity_order_release.sql`: sanctioned release creates one FEFO pick, remains Picking and retries safely.
- `deep_integrity_warehouse_intake.sql`: warehouse receipt queues one putaway without posting stock before placement.
- `product_movement_sale_loyalty.sql`: valid sale stock/customer posting remains atomic and idempotent. This also completes the extra check that expired during the previous repair turn.

The warehouse manager's attempted direct Refunded status was denied; it is not a finding. Personnel document insertion also has a real guard resetting supplied verification fields; suspected self-verification was excluded after inspecting that guard. The dormant performance/training service has unsafe fallback code, but no active caller was found, so it is not included among these fourteen operational findings.

## Repair order and limits

First address payment truthfulness and direct stock authority, then fulfillment/catalog/sales boundaries. Next bind hiring activation and disciplinary actions to trusted evidence and repair the recruitment compatibility path. Remove false success and confidential cache fallback alongside those commands.

This was a source, hook/service and live database investigation. It did not certify physical receiving/scanning, browser layouts, production configuration, external bank/mobile-money reconciliation or concurrent multi-device execution. Do not treat passed selected regressions as certification of the entire application.
